# 提交与版本发布全流程规范

> ⚠️ **提交与发布分离：日常小步提交不动版本号；版本号只在用户明确要求更新时才更新。**
> 当用户测试通过并明确要求「提交」或「发布」时，按本规范执行。

---

## 核心原则

- **日常提交**（用户说「提交」）：只做 Git 提交，**不修改版本号、不更新更新日志、不打 tag**。
- **版本号更新**（用户说「更新版号」/「发布」）：才升级版本号 + 整理更新日志 + Git 提交。
- **更新日志汇总制**：`更新日志.md` 顶部版本块 = 当前累积区。**未标记「已发布」的版本块可继续累积**，新改动写进该块，避免零碎版号；只有用户标记「已发布」后该块封顶，后续改动才需另起新版本块。
- **版号推进合并制**：若 `package.json` 版号已升（如 1.9.0→1.9.1），且旧版号块**未标记「已发布」**，则顶部块直接改为最新版号继续累积，**跳过的版号不单独记录**，累计内容随新块保留。即：未发布状态下只存在「最新版号」一个累积区，中间跳过的版号一律并入新版号。
- **更新日志自动写**：每次提交完成用户可感知的修复/优化后，AI **自动**把改动写入 `更新日志.md` 并单独提交，无需用户询问。写入规则：顶部版本块**未标记「已发布」** → 按最新版号累积写入该块；**已标记「已发布」** → 新起版本块并提醒用户升级版号。
- **版号状态标注由用户维护**：AI 正常写版号，**不标注发布状态**。用户主动标记「已发布」= 该版号已发布到私域、版本块封顶；AI 读更新日志时据此判断：顶部块已标记「已发布」则后续改动应新起版号块并提醒升级版号，未标记则继续累积。
- **重叠提醒**：当前版本块累积了多笔改动、且版号未更新时，AI 应在提交后**主动提醒用户**是否需要更新版号。

---

## 一、日常提交流程（小步提交）

### 1. 执行 Git 提交
- 只暂存本次涉及修改的代码文件（**不包含** `package.json`、`更新日志.md`）。
- **Commit Message 格式**：
  - 必须采用 `[类别] 具体的修改目标` 格式。
  - 前缀必须包含：`[修复]`、`[新增]`、`[优化]`、`[重构]`、`[文档]`、`[配置]` 或 `[发布]`。
  - 示例：`[修复] 修复文件夹封面收藏星标未实心显示`。
- 小步提交，保证可回退、易审查。

> ⚠️ 日常提交不要打 tag，tag 只用于正式发布。

---

## 二、正式发布流程（用户明确要求更新版号/发布时）

### 1. 修改版本号 (`package.json`)
- 根据自上次发布以来改动性质，自动升级补丁号（如 `1.8.6` -> `1.8.7`）。
- 若本次发布涉及较大功能新增，可考虑升级次版本号。

### 2. 更新更新日志.md
- 在顶部新建当前版本块，正常写版本号即可（如 `## v1.8.7`），**不标注发布状态**——「已发布」标记由用户发布后自行添加。
- **编写原则**：
  - **用户视角**：只写用户能直观感知的改进，绝不写“重构逻辑”、“修改 ESLint”、“触发自定义事件”等底层代码细节。
  - **汇总原则**：把自上一版本以来的多笔改动合并成 1~3 条用户可感知的改进。
  - **极简干练**：每条控制在 15 字以内，通俗易懂。
  - **分类前缀**：
    - `[新增]` 新功能/新特性
    - `[修复]` 修复异常/错误问题
    - `[优化]` 界面体验/性能优化

### 3. 执行 Git 提交
- 暂存本次发布涉及的全部代码文件、`package.json` 及 `更新日志.md`。
- Commit Message 格式：`[发布] 发布 vX.Y.Z`（示例：`[发布] 发布 v1.8.7`）。

### 4. 打 Git Tag 标签
- **默认不打 tag**：tag 由用户正式发布后自行处理。除非用户明确要求打 tag，否则提交后不执行 `git tag`。
