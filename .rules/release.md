# 发布与版本控制规范

## 一、 版本号修改时机
- **禁止提前修改**：在开发新功能或修复 Bug 的中途，禁止提前修改 `package.json` 中的版本号。
- **发布前修改**：仅在所有相关代码修改完成、功能验证/测试通过，并准备进行正式版本发布时，才修改 `package.json` 中的 `version` 字段。

---

## 二、 更新日志 (CHANGELOG.md) 编写规范
- **用户视角**：更新日志面向最终用户，精简通俗，拒绝长篇大论或暴露过多底层代码细节。
- **分类标准**：
  - `[新增]` / 🚀 新功能
  - `[修复]` / 🐛 问题修复
  - `[优化]` / 💡 体验与细节优化
- **保持精简**：多项零散修补合并为一条清晰简短的说明。

---

## 三、 Git 提交与 Tag 规范

### 1. 发布提交格式
修改 `package.json` 版本号和 `CHANGELOG.md` 后，使用统一的 Git 提交格式：
```bash
git add package.json CHANGELOG.md
git commit -m "[发布] 发布 vX.Y.Z"
```

### 2. 打 Git Tag 标签
发布提交完成后，必须为当前提交打上对应版本的 Git 标签：
```bash
git tag -a vX.Y.Z -m "[发布] vX.Y.Z"
```
*如需推送到远程仓库：*
```bash
git push origin main --tags
```

---

## 四、 常用类别前缀清单
提交普通代码时，使用以下统一前缀：
- `[修复]`：修复 Bug 或异常行为
- `[新增]`：添加新功能
- `[优化]`：性能、UI 或体验交互优化
- `[重构]`：重构代码架构（不改变功能）
- `[文档]`：更新 README、CHANGELOG 或规则文档
- `[配置]`：修改构建配置、依赖或环境变量
- `[发布]`：版本号升级与发布提交
