# 提交与版本发布全流程规范

> ⚠️ **当用户测试通过并明确要求「提交」、「发布」或「提交修复/功能」时，AI 必须严格按本规范的标准化流水线顺序执行！**

---

## 核心流程（必须按顺序连贯执行）

### 1. 修改版本号 (`package.json`)
- 根据本次改动的性质，自动升级 `package.json` 中的 `version`（小修补 upgrade 补丁号，如 `1.8.1` -> `1.8.2`）。

### 2. 更新 CHANGELOG.md
- 在 `CHANGELOG.md` 顶部插入新版本的更新日志。
- **编写原则**：
  - **用户视角**：只写用户能直观感知的改进，绝不写“重构逻辑”、“修改 ESLint”、“触发自定义事件”等底层代码细节。
  - **极简干练**：每条控制在 15 字以内，通俗易懂，1~3 条即可。
  - **分类前缀**：
    - `[新增]` 新功能/新特性
    - `[修复]` 修复异常/错误问题
    - `[优化]` 界面体验/性能优化

### 3. 执行 Git 提交
- 暂存涉及修改的代码文件、`package.json` 及 `CHANGELOG.md`。
- **Commit Message 格式**：
  - 必须采用 `[类别] 具体的修改目标` 格式。
  - 前缀必须包含：`[修复]`、`[新增]`、`[优化]`、`[重构]`、`[文档]`、`[配置]` 或 `[发布]`。
  - 示例：`[发布] 发布 v1.8.2` 或 `[修复] 修复转码状态丢失并发布 v1.8.2`。

### 4. 自动打 Git Tag 标签
- 提交完成后，必须为当前 Commit 打上版本标签：
  ```bash
  git tag -a vX.Y.Z -m "[发布] vX.Y.Z"
  ```
