# 提交与版本发布全流程规范

> ⚠️ **提交与发布分离：日常小步提交不动版本号、不写更新日志、不打 tag；发版由用户明确要求时统一执行。**
> 当用户测试通过并明确要求「提交」或「发布」时，按本规范执行。

---

## 核心原则

- **日常提交**（用户说「提交」）：只做 Git 提交，**不修改版本号、不更新更新日志、不打 tag**。
- **发版**（用户说「更新版号」/「发布」）：统一统计自上次发布以来的提交 → 决定版号 → 写更新日志 → Git 提交。
- **更新日志发版汇总制**：`更新日志.md` **只在发版时统一编写**，日常提交一律不写。发版前用 `git log` 统计本版本内全部提交，按用户视角合并成 1~3 条用户可感知的改进。
- **版号发版时决定**：每次发版重新决定版号，与更新日志一并落定，**无「累积区」「已发布」标记概念**——发布即版本块封顶，下一次发版另起新块。

---

## 一、日常提交流程（小步提交）

### 1. 执行 Git 提交
- 只暂存本次涉及修改的代码文件（**不包含** `package.json`、`更新日志.md`）。
- **Commit Message 格式**：
  - 必须采用 `[类别] 具体的修改目标` 格式。
  - 前缀必须包含：`[修复]`、`[新增]`、`[优化]`、`[重构]`、`[文档]`、`[配置]` 或 `[发布]`。
  - 示例：`[修复] 修复文件夹封面收藏星标未实心显示`。
- 小步提交，保证可回退、易审查。

### 2. 发版提醒
- 日常提交累积了多笔改动、且用户尚未要求发版时，AI 可在提交后**主动提醒用户**是否需要发版。

> ⚠️ 日常提交不要打 tag，tag 只用于正式发布。

---

## 二、正式发布流程（用户明确要求更新版号/发布时）

### 1. 统计提交
- 用 `git log <上次发布提交>..HEAD --oneline`（或用 tag）统计自上次发布以来全部提交，作为更新日志素材。

### 2. 决定版号 (`package.json`)
- 根据自上次发布以来改动性质，升级补丁号（如 `1.8.6` -> `1.8.7`）。
- 若本次发布涉及较大功能新增，可考虑升级次版本号。

### 3. 编写更新日志.md
- 在顶部新建当前版本块，正常写版本号即可（如 `## v1.8.7`）。
- **编写原则**：
  - **用户视角**：只写用户能直观感知的改进，绝不写"重构逻辑"、"修改 ESLint"、"触发自定义事件"等底层代码细节。
  - **汇总原则**：把本版本多笔提交合并成 1~3 条用户可感知的改进。
  - **极简干练**：每条控制在 15 字以内，通俗易懂。
  - **分类前缀**：
    - `[新增]` 新功能/新特性
    - `[修复]` 修复异常/错误问题
    - `[优化]` 界面体验/性能优化

### 4. 执行 Git 提交
- 暂存本次发布涉及的全部代码文件、`package.json` 及 `更新日志.md`。
- Commit Message 格式：`[发布] 发布 vX.Y.Z`（示例：`[发布] 发布 v1.8.7`）。

### 5. 打 Git Tag 标签
- **默认不打 tag**：tag 由用户正式发布后自行处理。除非用户明确要求打 tag，否则提交后不执行 `git tag`。
