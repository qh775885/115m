# 发布规则

## 变更识别与对比策略
- **强制跨版本比对**：发布前必须通过 `git log <上一个tag>..HEAD` 获取自上个正式版本以来的所有提交记录。
- **获取上个版本**：使用 `git describe --tags --abbrev=0` 确定上一个发布标签。

## 更新说明生成规范
- **面向用户**：发布说明默认写给用户看。从原始提交记录中提取“用户能感知到”的价值，不要包含内部重构细节、代码结构调整、ESLint 等纯技术内容。
- **分类汇总**：根据提取出的关键更新，将变更系统性地分为以下几类（至少包含）：
  - 🚀 **新功能**
  - 🐞 **问题修复**
  - ⚡ **体验优化**
- **合并同类项**：将多次相关修改（例如 UI 的连续几次微调、音量控件的多次修复）合并为一条连贯、易读的更新说明，避免碎片化和流水账。
- **历史追溯**：因为可能会有较长时间不更新的情况，生成的说明必须覆盖两个版本之间的完整闭环，让用户知道这个版本到底积累了哪些改进。

## 发布执行流程
1. **生成与确认**：基于跨版本提交记录生成更新说明，可以展示给用户确认或直接保存备用。
2. **升版号**：更新 `package.json` 中的版本号。
3. **构建打包**：执行打包，生成最新的 zip 安装包。
4. **电报推送 (核心)**：不需要强制在 GitHub 上创建 Release。只需使用本地终端的 `curl` 调用 Telegram Bot API（让用户提供或确认环境变量 `TELEGRAM_BOT_TOKEN` 和 `TELEGRAM_CHAT_ID`），将更新说明和生成的 zip 安装包直接推送至电报频道。
5. **打标签 (可选)**：根据用户意愿，用 `git tag` 标记一下当前版本以便后续对比，但不需要推送到 GitHub Release。
6. **限制范围**：此规则只在明确讨论发版、推送更新或打包操作时使用，不扩展到无关开发任务。
